Model Context Protocol, explained with three tiny servers: weather, hardware, and file IO.

1. What is MCP?

An LLM on its own can only produce text. It cannot check today's weather, read your disk, or save a file. Model Context Protocol (MCP) is an open standard that lets any AI application discover and call tools that live in separate programs. Think of it as USB-C for AI tools: write a tool once as an MCP server and any MCP client can use it.

PieceRoleIn this project
MCP serverExposes tools (also resources and prompts) over a standard protocolThe three *_server.py files
MCP clientConnects to servers, lists their tools, forwards callsclient.py
LLMDecides which tool to call and with what arguments. It never runs tools itself.Ollama llama3.2
TransportHow messages travel. stdio = client launches the server as a subprocess and talks over stdin/stdoutstdio (simplest; no ports)
The loop to remember:
  1. Client asks each server list_tools (discovery).
  2. Client gives those tool descriptions to the LLM with the user's question.
  3. LLM replies "call get_current_weather(city="Pune")".
  4. Client sends call_tool to the right server and gets the result.
  5. Result goes back to the LLM, which writes the final answer.

3. Weather server

Uses Open-Meteo: free, no API key. Two calls: geocode the city name to latitude/longitude, then fetch current conditions.

from mcp.server.fastmcp import FastMCP
import httpx

mcp = FastMCP("weather", log_level="WARNING")

@mcp.tool()
def get_current_weather(city: str) -> str:
    """Get the current weather for a city, e.g. 'Pune' or 'London'."""
    geo = httpx.get(GEO_URL, params={"name": city, "count": 1}).json()
    place = geo["results"][0]
    wx = httpx.get(WX_URL, params={
        "latitude": place["latitude"], "longitude": place["longitude"],
        "current": "temperature_2m,relative_humidity_2m,wind_speed_10m,weather_code",
    }).json()["current"]
    return f"{place['name']}: {wx['temperature_2m']} C, ..."

if __name__ == "__main__":
    mcp.run()          # stdio transport
What FastMCP does for you: the @mcp.tool() decorator turns the function into a tool. The function name becomes the tool name, the docstring becomes the description the LLM reads, and the type hints become a JSON Schema for the arguments. Write a good docstring: it is the LLM's only documentation.

Sample result: Pune, India: 27.9 C, humidity 48%, wind 7.5 km/h (WMO code 0)

4. Hardware server

Same pattern, no network: read local facts with psutil and platform. Small, focused tools are easier for a small model to pick correctly than one giant tool.

@mcp.tool()
def get_memory_info() -> str:
    """Total and used RAM."""
    m = psutil.virtual_memory()
    return f"RAM: {m.total / GB:.1f} GB total, {m.used / GB:.1f} GB used ({m.percent}%)"

@mcp.tool()
def get_system_summary() -> str:
    """One-shot summary: OS, CPU, RAM and disk."""
    return "\n".join([os_line, get_cpu_info(), get_memory_info(), get_disk_info()])

Tools: get_cpu_info, get_memory_info, get_disk_info, get_system_summary. Sample output:

5. File IO server

Giving a model file access is powerful, so we sandbox it: every path is resolved inside ./sandbox and anything that escapes (like ../client.py) is rejected.

ROOT = (Path(__file__).parent / "sandbox").resolve()

def _safe(name: str) -> Path:
    p = (ROOT / name).resolve()
    if not p.is_relative_to(ROOT):
        raise ValueError("Access outside the sandbox is not allowed")
    return p

@mcp.tool()
def read_file(name: str) -> str:
    """Read a text file from the sandbox."""
    return _safe(name).read_text(encoding="utf-8")

@mcp.tool()
def write_file(name: str, content: str) -> str:
    """Create or overwrite a text file in the sandbox."""
    _safe(name).write_text(content, encoding="utf-8")
    return f"Wrote {len(content)} chars to {name}"

Tools: list_files, read_file, write_file, append_file, delete_file.

Security lesson: an MCP server runs with your permissions, and the LLM chooses the arguments. Always validate inputs inside the tool; never trust the model. Exceptions are returned to the client as tool errors (isError=true), so the model can see what went wrong.

6. The client

This is where MCP meets Ollama. Three steps in client.py:

Step A - launch servers and discover tools

params = StdioServerParameters(command=sys.executable, args=["weather_server.py"])
read, write = await stack.enter_async_context(stdio_client(params))
session = await stack.enter_async_context(ClientSession(read, write))
await session.initialize()                      # MCP handshake
tools = (await session.list_tools()).tools      # discovery

Step B - translate MCP tool schema to Ollama's format

{"type": "function", "function": {
    "name": t.name,
    "description": t.description,
    "parameters": t.inputSchema}}              # already JSON Schema

MCP's inputSchema is plain JSON Schema, which is exactly what Ollama expects, so the translation is trivial. We also keep a dict routes[tool_name] = session so we know which server owns each tool. With three servers connected, the model sees all ten tools at once.

Step C - the tool loop

while True:
    resp = await client.chat(model=MODEL, messages=messages, tools=specs)
    msg = resp.message
    messages.append(msg)
    if not msg.tool_calls:
        return msg.content                      # final answer
    for call in msg.tool_calls:
        result = await routes[call.function.name].call_tool(
                     call.function.name, dict(call.function.arguments))   # MCP call
        text = "".join(c.text for c in result.content if c.type == "text")
        messages.append({"role": "tool", "tool_name": call.function.name, "content": text})

The loop repeats because one question may need several tool calls (weather, then RAM, then write a file).

8. Gotchas and exercises

  • Small models make mistakes. In testing, llama3.2 (3B) asked to chain weather + RAM + write a note picked the right tools but wrote a placeholder ({memory} MB) into the file. The protocol worked; the model's reasoning did not. Use a bigger model (qwen3:8b, gpt-oss) or split the request into steps.
  • The model must support tools. Not every Ollama model does; check the "tools" tag on its page.
  • Never print to stdout in a stdio server. stdout carries the protocol; use stderr or logging.
  • Too many tools confuse small models. Keep descriptions short and distinct.
