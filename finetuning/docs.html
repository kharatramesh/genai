1 · Concept

What fine-tuning is

A large language model learns in stages. Pre-training on trillions of tokens teaches it language and world knowledge. Instruction tuning teaches it to follow requests and chat. Fine-tuning is the last stage, where you continue training on a few hundred to a few thousand examples of your task. Then the model behaves the way you need: your output format, your tone, your domain vocabulary, your refusal rules.

Prompting vs RAG vs fine-tuning

They solve different problems, and production systems often combine them.

TechniqueChangesBest for
PromptingThe input onlyQuick behaviour tweaks, few examples
RAGKnowledge supplied at query timeFacts that change, citations, large document sets
Fine-tuningThe model's weightsFormat, style, domain skill, latency (shorter prompts), smaller models
RAG + FTBothA model trained to use retrieved context well. This is our demo.

Rule of thumb

RAG gives the model knowledge. Fine-tuning gives the model skill.

Don't fine-tune facts that change weekly into weights: re-indexing a document is cheaper than retraining. Fine-tune the behaviour: read the passages, pick the right one among look-alikes, answer in one short line, and say "I don't know" when the answer isn't there.

  • Data: 500–5,000 clean examples beat 100,000 noisy ones.
  • Evaluation first: measure the base model before you train, so you can prove the gain.
  • Hold out evaluation data the model never sees during training.
2 · The problem

Why full fine-tuning is expensive

Full fine-tuning updates every weight. With the Adam optimizer in mixed precision, each parameter costs about 16 bytes of GPU memory before you count activations. That's 8× the size of the model you are fine-tuning.

3 · Parameter-efficient fine-tuning

LoRA: train a small update, freeze the rest

LoRA (Low-Rank Adaptation, Hu et al. 2021) is based on an observation: the change a model needs during fine-tuning has low rank. Instead of learning a full update ΔW for a d × k weight matrix, LoRA learns two thin matrices B (d × r) and A (r × k) with r ≪ d. The original W stays frozen.

LoRA hyper-parameters used in this lab

SettingValueWhat it does
r16Rank of A and B: capacity of the update.
lora_alpha32 (= 2r)Scales the update by α/r. Keeping α = 2r means you rarely retune the LR when you change r.
target_modules"all-linear"Adapters on attention and MLP layers. Better than attention-only for most tasks.
lora_dropout0.05Regularization for small datasets.
learning_rate2e-4About 10× higher than full fine-tuning; adapters start at zero.
batch4 × 4 accumulation = 16Use --batch-size 1 on small GPUs; accumulation keeps the effective batch at 16.
4 · Quantized LoRA

QLoRA: the same adapters on a 4-bit base

With LoRA, the frozen base weights dominate memory. QLoRA (Dettmers et al. 2023) stores them in 4 bits instead of 16. That cuts their size about 3.5×, enough to fine-tune a 65B model on one 48 GB GPU. Each layer is de-quantized to 16-bit just in time for its matrix multiply. Gradients flow through it into the 16-bit adapters.

LoRA or QLoRA?

LoRAQLoRA
Base weights16-bit4-bit NF4
GPU memory~2 bytes / param~0.5–0.7 bytes / param
SpeedFaster~20–40% slower (de-quantization)
QualityReferenceUsually within noise of LoRA
HardwareAny GPU, or CPU for tiny modelsNVIDIA GPU (bitsandbytes)
Pick it whenThe 16-bit model fits in VRAMIt doesn't, or you want a bigger model on the same GPU

6 · The demo

Fine-tuning a model for RAG

We reuse the documents from the RAG module: HR policies, support FAQs, product manuals, incident reports and lab notebooks, as .txt and .pdf. They are hard for RAG on purpose. Every document holds dozens of near-identical paragraphs that differ only in names, numbers and IDs. Retrieval returns three look-alike passages, and a small base model often picks the wrong one, rambles, or invents an answer.

Why evaluate on held-out passages? The 99 eval passages are in the RAG index but were never in a training example. If the fine-tuned model answers them better, it has learned the reading skill, not memorized facts. That's the property that survives when your documents change.

def example(question, answer, fact):
    pool = [p for p in distractors[fact["kind"]] if p != fact["passage"]]
    if random.random() < args.negatives:              # 20%: golden passage hidden
        context, answer = random.sample(pool, TOP_K), IDK
    else:
        context = random.sample(pool, TOP_K - 1) + [fact["passage"]]
        random.shuffle(context)                             # answer can sit at any rank
    return {"prompt": build_messages(question, context),
            "completion": [{"role": "assistant", "content": answer}]}

How the answer-only masking works (common.load_train_dataset) 
def encode(row):
    prompt = tok.apply_chat_template(row["prompt"], tokenize=False, add_generation_prompt=True)
    full = tok.apply_chat_template(row["prompt"] + row["completion"], tokenize=False)
    prompt_ids = tok(prompt, add_special_tokens=False)["input_ids"]
    answer_ids = tok(full[len(prompt):], add_special_tokens=False)["input_ids"]
    return {"input_ids": prompt_ids + answer_ids,
            "labels":    [-100] * len(prompt_ids) + answer_ids}   # -100 = ignored by the loss

We use the plain transformers.Trainer here instead of TRL's SFTTrainer. The masking stays visible to participants, and recent TRL releases need Triton GPU kernels, which can't train on CPU and need an extra install on Windows.

Step 6 · Size report

python 06_size_report.py
def lora_params(a, r):
    """A LoRA pair on a d_in x d_out layer adds r * (d_in + d_out) parameters."""
    h, m, kv = a["hidden"], a["mlp"], a["kv"]
    per_layer = (h + h) + (h + kv) * 2 + (h + h) + (h + m) * 2 + (m + h)   # q, k, v, o, gate, up, down
    return a["layers"] * r * per_layer
