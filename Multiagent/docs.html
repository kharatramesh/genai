0. The big picture

One agent with 25 tools gets confused: the prompt is long, the tool list is long, and the model picks the wrong tool. A multi-agent system splits the work into specialists, each with a short prompt and a few tools, and puts an orchestrator in front that decides who does what.

Every agent folder has the same three files: tools.py (what it can do), agent.py (prompt + model + build()) and run.py (run it alone). That shape repeats, so once students understand one agent they can read all four.

2. Offline vs online models

Theory
Offline (Ollama)Online (Claude API)
Data privacyNothing leaves the machinePrompt and tool output go to the provider
CostFree after download; uses your CPU/GPUPay per token
QualityGood for narrow tasks; weaker at planningStronger reasoning and tool use
AvailabilityWorks without internetNeeds network and an API key
How we split them: the file agent and system monitor read local data (file contents, process lists), so they stay offline. Container management and trace analysis benefit from stronger reasoning and handle no private file contents, so they go online. Because every agent gets its model from one factory, moving an agent between offline and online is a one-word change.

3. The ReAct agent building block

Theory: ReAct = Reason + Act The model looks at the conversation and either answers or asks for a tool. If it asks for a tool, we run it, add the result to the conversation, and ask the model again. In LangGraph this is a graph with two nodes and a loop: 
START → model ──(tool_calls?)──yes──► tools ──┐
          ▲                                    │
          └────────────────────────────────────┘
          └──no──► END
  • State: MessagesState, a list of messages that every node appends to.
  • Node: a Python function state → partial update.
  • Conditional edge: tools_condition routes to "tools" if the last AI message has tool calls, else to END.
  • bind_tools sends each tool's name, docstring and argument schema to the model. The docstring is the tool's prompt, so write it carefully.
Code: common/react.py (all four agents are built with this) 
def build_react_agent(llm, tools, system_prompt: str, name: str, checkpointer=None):
    llm_with_tools = llm.bind_tools(tools)

    def call_model(state: MessagesState):
        msgs = [SystemMessage(system_prompt)] + state["messages"]
        return {"messages": [llm_with_tools.invoke(msgs)]}

    g = StateGraph(MessagesState)
    g.add_node("model", call_model)
    g.add_node("tools", ToolNode(tools, handle_tool_errors=True))  # tool exceptions -> error text for the LLM
    g.add_edge(START, "model")
    g.add_conditional_edges("model", tools_condition)  # tool call -> "tools", else END
    g.add_edge("tools", "model")
    return g.compile(name=name, checkpointer=checkpointer)
Teaching point 1: handle_tool_errors=True turns a tool exception (missing file, bad path, invalid container name) into a ToolMessage the model can read and react to. Without it, LangGraph's default only catches bad-argument errors; any other exception crashes the whole run.
Teaching point 2: when an agent runs inside the orchestrator we pass checkpointer=None. The sub-graph then uses the parent's checkpointer, which is what lets an interrupt deep inside a tool pause the whole system.

4. Human in the loop (HITL)

Theory Agents should not delete files or containers on their own. LangGraph's interrupt(payload):
  1. pauses the graph and saves its state with the checkpointer (keyed by thread_id);
  2. returns control to the caller with the payload (shown as __interrupt__ in the stream);
  3. the caller shows it to a human and calls graph.stream(Command(resume=answer), config). If several interrupts are pending at once (the model asked for two risky tools in one step), resume with a dict {interrupt.id: answer}, one entry per interrupt;
  4. the interrupted node re-runs from the top, and this time interrupt() returns answer.
Because of point 4, always ask for approval before any side effect in the tool. Anything above the interrupt() line runs twice.

This project has two approval points:

  • Tool level: risky tools call require_approval() (delete or overwrite a file; run, stop, restart or remove a container).
  • Plan level (optional, APPROVE_PLAN=1): the orchestrator shows the whole plan before running it.
When the human says no, the tool returns a rejection message to the LLM instead of raising an error, so the agent can explain what happened.
Code: common/hitl.py 
from langgraph.types import interrupt

def require_approval(action: str, details: str) -> tuple[bool, str]:
    """Ask a human. Returns (approved, feedback)."""
    if os.getenv("AUTO_APPROVE") == "1":
        return True, ""
    answer = interrupt({"type": "approval", "action": action, "details": details})
    if isinstance(answer, dict):
        return bool(answer.get("approved")), str(answer.get("feedback", ""))
    return str(answer).strip().lower() in {"y", "yes", "approve", "approved", "ok"}, ""


def rejected(feedback: str = "") -> str:
    """Text handed back to the LLM so it can react to a 'no'."""
    return "REJECTED by human operator." + (f" Reason: {feedback}" if feedback else "") + \
        " Do not retry this action; tell the user it was not performed."
The caller side: common/cli.py 
def run_turn(app, payload, config) -> str:
    """Run one user request to completion, looping while the graph asks for approval."""
    final = ""
    while True:
        pending = []
        for chunk in app.stream(payload, config, stream_mode="updates"):
            for node, update in chunk.items():
                if node == "__interrupt__":
                    pending.extend(update)  # several, if the model asked for 2+ risky tools at once
                    continue
                print(f"  [{node}]")
                ...
        if not pending:
            return final
        payload = Command(resume={i.id: ask_human(i.value) for i in pending})  # answer each interrupt by id
i.value is the payload passed to interrupt(); i.id tells LangGraph which paused call each answer belongs to.

5. Agent 1: File manager offline

Theory
  • Least privilege: the agent only sees Multiagent/workspace/. _safe() resolves every path and refuses anything that escapes it, such as ../../secrets.txt.
  • Safe by default: creating a new file is allowed; overwriting or deleting asks a human.
  • Offline because file contents are private data.
Code: file_agent/tools.py (excerpt) 
WORKSPACE = Path(__file__).resolve().parent.parent / "workspace"

def _safe(name: str) -> Path:
    """Resolve inside the workspace; refuse '../' escapes."""
    p = (WORKSPACE / name).resolve()
    if p != WORKSPACE and WORKSPACE not in p.parents:
        raise ValueError(f"Path '{name}' is outside the workspace")
    return p

@tool
def delete_file(filename: str) -> str:
    """Delete a file from the workspace. Requires human approval."""
    p = _safe(filename)
    if not p.is_file():
        return f"'{filename}' does not exist"
    ok, why = require_approval("delete_file", f"Permanently delete '{filename}'")
    if not ok:
        return rejected(why)
    p.unlink()
    return f"Deleted {filename}"

TOOLS = [list_files, read_file, write_file, delete_file, search_in_files]
Code: file_agent/agent.py 
DESCRIPTION = "create, read, search, list and delete files in the workspace folder"
PROMPT = ("You are the File Manager agent. You only manage files inside the workspace using your tools. "
          "Never invent file contents you have not read. Be concise.")

def build(checkpointer=None):
    return build_react_agent(offline_llm(), TOOLS, PROMPT, name="file_agent", checkpointer=checkpointer)

7. Agent 3: Container manager online

Theory: container lifecycle 
  image ──run──► running ──stop──► exited ──start──► running
                    │                 │
                 restart            remove (rm -f)  ──► gone (data in the container layer is lost)
  • We call the docker CLI with an argument list (subprocess.run(["docker", ...])), never a shell string, so the LLM cannot inject ; rm -rf /.
  • Names, images and port mappings are validated with regexes before use.
  • State-changing actions (run, stop, restart, remove) need approval. Inspection (list, logs, stats) and start do not.
  • Online because multi-step lifecycle work ("replace the web container with a new image on port 8081") needs stronger reasoning.
Code: container_agent/tools.py (excerpt) 
def _docker(*args: str, timeout: int = 120) -> str:
    if not shutil.which("docker"):
        return "ERROR: docker CLI not found. Install Docker Desktop and make sure it is running."
    r = subprocess.run(["docker", *args], capture_output=True, text=True, timeout=timeout)
    return (r.stdout + r.stderr).strip()[:4000] or "(no output)"

@tool
def run_container(image: str, name: str, port_mapping: str = "") -> str:
    """Create and start a detached container, e.g. image='nginx:alpine', name='web', port_mapping='8080:80'. Needs approval."""
    _check(name)
    ...
    cmd = ["run", "-d", "--name", name] + (["-p", port_mapping] if port_mapping else []) + [image]
    ok, why = require_approval("run_container", "docker " + " ".join(cmd))
    return _docker(*cmd, timeout=300) if ok else rejected(why)

TOOLS = [list_containers, list_images, run_container, start_container, stop_container,
         restart_container, remove_container, container_logs, container_stats]

8. Observability with Langfuse

Theory With five LLM-driven components, "why did it do that?" is hard to answer from the terminal. Langfuse records a trace per request, with nested observations for every graph node, LLM call (prompt, output, tokens, cost, latency) and tool call.
  • LangChain and LangGraph emit callbacks. Langfuse's CallbackHandler listens to them, so no agent code changes: we attach the handler once in the run config and it reaches every sub-graph.
  • metadata.langfuse_session_id groups all turns of one chat into a session.
  • thread_id (LangGraph) and session_id (Langfuse) use the same value so you can match a paused graph to its trace.
Code: common/tracing.py 
def make_config(session_id: str | None = None, **extra) -> dict:
    """Build the LangGraph run config: thread id (for memory/interrupts) + Langfuse callback."""
    session_id = session_id or uuid.uuid4().hex[:8]
    config = {"configurable": {"thread_id": session_id}, "recursion_limit": 40, **extra}
    if langfuse_enabled():
        from langfuse.langchain import CallbackHandler
        config["callbacks"] = [CallbackHandler()]
        config["metadata"] = {"langfuse_session_id": session_id}
    return config
Practical
  1. Create a free project at cloud.langfuse.com (or self-host with docker compose from the Langfuse repo) and copy the keys into .env.
  2. Run any agent. The banner should say Langfuse tracing: ON.
  3. In the Langfuse UI, open Traces and click one: you'll see planner → system_agent → model → tools → ... as a tree, with tokens and latency on each LLM call.
  4. Open Sessions to see a whole conversation, including the turn that paused for approval.

9. Agent 4: Agent monitor online

Theory: an agent that watches agents Langfuse stores the telemetry. The monitor agent reasons about it: "which agent is slowest?", "did anything fail in the last hour?", "how much did today cost?". Its tools call the Langfuse public API through the SDK client. It is online because summarising lots of trace data needs a strong model, and traces hold metadata, not your files.

Note: before reading, the tools call flush() so traces from the current session are sent first. Langfuse still takes a few seconds to ingest them, so very fresh traces may be missing.

10. The LangGraph orchestrator

Theory: two orchestration patterns
PatternHow it worksGood for
Supervisor loopAfter every worker, an LLM decides "who's next, or FINISH?"Strong models; open-ended tasks
Plan-and-execute (used here)An LLM writes the full ordered plan once; the graph runs it step by step; a final node summarisesSmall local models; predictable, auditable runs
A lesson from building this: we first wrote a supervisor loop on qwen3:8b. For "check RAM, then save it to ram.txt" it routed to system_agent, then said FINISH and claimed the file was saved, although file_agent never ran. Small models are bad at tracking "what's left?" across a loop. Planning once, then running each step in code, fixed it. Put control flow in the graph, not in the prompt.
  • Structured output: with_structured_output(Plan) forces the model to return valid JSON that matches a Pydantic schema, so routing never depends on parsing free text.
  • Custom state: plan, idx (current step) and reports sit next to messages.
  • Context passing: each worker gets its own task plus the earlier reports, never the raw chat history. That keeps prompts short and avoids conversations that end on an assistant turn, which some APIs reject.
  • The begin node resets plan/idx/reports for every new user turn. The checkpointer keeps state between turns, so without the reset an old plan would leak into the next request.
  • Why approve_plan is its own node: on resume, the interrupted node re-runs from the top. If the interrupt sat inside planner, resuming would call the LLM again and could run a different plan from the one the human approved. In a separate node, only the approval re-runs and it reads the plan already saved in state. (This is step 4's "no side effects before interrupt()" rule; an LLM call counts.)
START → begin → planner → approve_plan ─┬─► file_agent ──────┐
                                        ├─► system_agent ────┤   each worker → next_step()
                                        ├─► container_agent ─┤   = plan[idx].agent  or  "summarize"
                                        ├─► monitor_agent ───┘
                                        └─► summarize → END
Code: supervisor/graph.py (core) 
class Step(BaseModel):
    agent: Literal["file_agent", "system_agent", "container_agent", "monitor_agent"]
    task: str = Field(description="self-contained instruction for that agent, with all names/values it needs")

class Plan(BaseModel):
    """Ordered steps needed for the request. Empty list if no agent is needed."""
    steps: list[Step]

class State(MessagesState):
    plan: list[dict]
    idx: int
    reports: list[str]

def planner(state):
    plan = planner_llm.invoke([SystemMessage(PLANNER_PROMPT), HumanMessage(last_user_text(state["messages"]))])
    return {"plan": [s.model_dump() for s in plan.steps]}

def approve_plan(state):                                     # HITL #2: approve the whole plan
    if not state["plan"] or os.getenv("APPROVE_PLAN") != "1":
        return {}
    answer = interrupt({"type": "approval", "action": "execute_plan", "details": ...})
    if not (isinstance(answer, dict) and answer.get("approved")):
        return {"plan": [], "reports": ["Plan rejected by human operator."]}
    return {}

def next_step(state) -> str:
    return state["plan"][state["idx"]]["agent"] if state["idx"] < len(state["plan"]) else "summarize"

def worker(state, config):                                   # one per agent, built by make_worker()
    step = state["plan"][state["idx"]]
    task = step["task"] + "\n\nResults of previous steps:\n" + "\n".join(state["reports"])
    result = agent.invoke({"messages": [HumanMessage(task)]}, config)   # config carries Langfuse + checkpointer
    report = f"[{name}] {result['messages'][-1].content}"
    return {"idx": state["idx"] + 1, "reports": state["reports"] + [report], "messages": [AIMessage(report, name=name)]}

g = StateGraph(State)
g.add_node("begin", begin); g.add_node("planner", planner)
g.add_node("approve_plan", approve_plan); g.add_node("summarize", summarize)
g.add_edge(START, "begin"); g.add_edge("begin", "planner"); g.add_edge("planner", "approve_plan")
g.add_conditional_edges("approve_plan", next_step, [*WORKERS, "summarize"])
for name, module in WORKERS.items():
    g.add_node(name, make_worker(name, module))
    g.add_conditional_edges(name, next_step, [*WORKERS, "summarize"])
g.add_edge("summarize", END)
app = g.compile(checkpointer=checkpointer)

12. Lab exercises

  1. Swap models: make system_agent online and container_agent offline. Compare answer quality and latency in Langfuse.
  2. New tool: add a kill_process(pid) tool to the system monitor, protected by require_approval.
  3. Fifth agent: create network_agent/ (ping, DNS lookup) with the same three-file layout and register it in WORKERS. Also add it to the Literal in Step.
  4. Persistent memory: replace InMemorySaver with SqliteSaver (pip install langgraph-checkpoint-sqlite) and resume a paused approval after restarting Python.
  5. Edit, don't just approve: let the human change the arguments (for example a different port) by returning {"approved": True, "args": {...}} from ask_human.
  6. Langfuse scores: after each answer, ask "was this helpful? 1-5" and send it with langfuse.create_score(...).
